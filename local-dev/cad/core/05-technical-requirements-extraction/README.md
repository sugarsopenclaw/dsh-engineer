# 05 · 技术要求提取

核心实现只有一个源文件：`TechnicalRequirementsExtractor.cs`。

它从图框内的普通文字中提取“技术要求”标题、编号条目和续行，不引用 THCAD、Teigha、BricsCAD、COM、文件系统或 JSON。THCAD Adapter 只把文字内容、图层、句柄和包围盒转成普通输入。

## 当前识别依据

- 标题文字包含“技术要求”，不要求必须完全等于它，也不要求居中；
- 从标题下方寻找同图层、同一文字列中的 `1.`、`2.` 等编号文字；
- 按图面从上到下保持源编号，不把“必须严格 1–N”当作提取前提；
- 两个编号之间缩进相近的无编号文字并入上一条，保留每个来源文字句柄；
- 标题通常位于右上区域只是沈变七图的有效观察，不是硬编码条件。

例如上节油箱源图从第 5 条直接到第 7 条，算法仍会完整提取这段正文，并在质量结果和 Markdown 中报告缺号 6。

## 两层输出

- `technical-requirements.json`：机器证据层，包含标题、每条原始文字、合并正文、句柄、包围盒、缺号和重号；
- `technical-requirements.md`：阅读层，只保留图纸名、整理后的技术要求正文和编号检查，适合直接提供给人或 LLM；
- 同一 JSON 结果也挂在 `semantic-objects.json.technical_requirements`，并附带 03 计算出的图框分区位置。

Markdown 是 JSON 的派生视图，不替代原始证据。

## 当前边界

- 必须存在明确的“技术要求”标题；
- 当前只组织 DBText/MText，且默认正文与标题同图层；
- 依赖图框和文字包围盒做空间分组，不从图片像素 OCR；
- 没有编号的整段技术要求、多个并排编号栏等新排版需要积累样本后再扩展；
- 只整理源文和报告编号异常，不擅自补写缺失内容。
