## 先把哪份资料当真

本次实际核对了 4 份客户资料和 1 份 DOCX 内嵌附件：

1. 原始优先级 XLSX：13 项图纸审核与设计辅助需求，是一级需求和优先顺序的主证据；
2. 原始访谈 DOCX：4 类审核场景、1 类送审图转换、1 类生产 DXF 净化；
3. DOCX 内嵌《沈阳特变电图纸删除效果说明》：生产 DXF 删除步骤的主证据；
4. 两份 Markdown 整理稿：属于专业二次分析，只辅助拆分，不能覆盖原始客户表述。

原始 XLSX 明确“从上到下，优先级从高到低”。序号 4、6 为黄色，序号 5 为红色，但没有颜色图例，因此只保留原始颜色，不推断它代表风险、紧急度或研发状态。

内嵌删除说明明确写出：部分非标准标注可能漏删或误删，侧视图和俯视图无法单独判断，建议人工处理。因此整理稿中的“已形成完整标准化删除执行规则”不能作为客户已确认事实。模型同时保留两份证据及其权威等级，后续由客户决定如何闭合。

## 20 个一级业务需求

一级名称有意使用客户能直接理解的朴素表达，不使用 `R-01`、`S1` 或算法名称代替业务含义。

### 原优先级表的 13 项

1. 审核图纸上的尺寸标注；
2. 审核专用件图号能不能借用；
3. 核对各部件明细、主材清单和产品 BOM；
4. 比较前期图、送审图和生产图，找出差异和矛盾；
5. 核对图纸 BOM 和图面上实际画出的部件；
6. 核对总图、布置图和部件图的关键尺寸；
7. 审核图纸技术要求；
8. 提示尺寸逻辑冲突和装配干涉；
9. 用相似产品图纸帮助复核当前设计；
10. 按企业设计原则和规定逐条审图；
11. 用自然语言让 AI 受控修改 DWG；
12. 核对标注尺寸、实际几何、单位和比例；
13. 用二维图纸辅助生成 Creo 三维模型。

### 原访谈的 7 个场景

1. 审核 17 类组部件图纸；
2. 校验铁心叠片图和总图是否一致；
3. 核对绕组图纸、算单、主材表和规范；
4. 核对绕组组装关系；
5. 根据算单自动生成出头位置示意图；
6. 把内部布置图转换成外部送审图；
7. 把送审或零件 DWG 净化成生产用 DXF。

原访谈把“绕组组装校验”和“出头示意图生成”写在同一个场景中。本模型把它们拆为两个一级需求，因为一个是检查已有设计，一个是生成新图；输入、权限、失效方式和验收标准不同。

## 什么叫“拆到不可再拆”

这里的原子需求不是 CAD API 的最小调用，也不是代码函数的最小语句，而是业务上能够单独回答“做没做到”的最小结果：

- 只表达一个观察、比较、生成、输出或约束；
- 有单一的验证方法；
- 失败时能明确指向这一点，而不是整组功能；
- 再往下拆只会进入算法步骤、CAD 实体字段或具体能力调用，那些属于 logic/能力图谱，不属于业务需求图谱。

例如“审核图纸上的尺寸标注”继续拆为“判断哪些特征必须有尺寸”“检查完整性”“检查正确性和规范性”；其叶子再落到“报告孔径、孔距和孔定位尺寸缺失”“检查关键尺寸公差”“检查跨视图数量和尺寸”等可独立验收点。

所有领域拆分都标为 `domain_decomposition`。如果缺少客户规则、公差、样本或权威数据源，相应原子需求会标记 `needs_confirmation=true`，不会伪装成已经确认的客户事实。

## 为什么是 DAG，不是一棵硬树

“审核 17 类组部件图纸”会复用尺寸标注、BOM、图面实例、跨图接口、技术要求和设计规定等横向需求；“绕组综合校验”也会复用 BOM、技术要求和规则适用性。如果给每个场景复制一份相同叶子，名字和规则很快会漂移。

因此需求结构是有向无环图：

- `contains_requirement`：组合 20 个一级业务需求；
- `decomposes_to`：把大需求拆成小需求；
- `reuses_requirement`：场景复用已经存在的横向需求，不复制节点。

关系自身还要记录展示顺序、拆分理由和关系来源，所以使用对象化关系 `RequirementRelation`，而不是只存一个 `parent_id`。

已记录的关键去重决定包括：

- “尺寸标注审核”与“标注值/实测几何/单位比例”不合并，只共享测量能力；
- “版本差异”与“跨图接口一致性”不合并；
- “17 类组部件综合审核”保留为业务场景，复用六类横向审图需求；
- “绕组综合校验”保留专业范围，复用通用 BOM、技术要求和规则审查；
- “绕组组装校验”与“出头图生成”拆开；
- “内部图转送审图”与“生产 DXF 净化”不合并。

## 按 Palantir 思路补哪些对象和数据表

Palantir 把 Ontology 定义为组织真实对象之上的运营层，同时包含语义元素（对象、属性、链接）和动力元素（动作、函数）；目标不是画一张静态知识图，而是支撑真实工作流。[Ontology overview](https://www.palantir.com/docs/foundry/ontology/overview)

其结构指导强调三点与本项目直接相关：事实只存一次；带日期、角色、状态等元数据的关系应建成对象化链接；名称应让领域人员和 Agent 都能直接理解。[Ontology structural guidance](https://www.palantir.com/docs/foundry/ontology/ontology-structural-guidance)

因此首批数据不是只有一张 `requirements` 表，而是下面几组对象：

### 需求事实

- `requirement_nodes`：需求 ID、朴素名称、类型、来源层级、是否原子、候选验证方法、优先级和确认状态；
- `requirement_relations`：父需求、子需求、包含/拆分/复用类型、顺序和理由；
- `requirement_aliases`：原称、规范称和模糊称谓；
- `dedup_decisions` 与 `dedup_decision_requirement_links`：去重决定及其涉及的需求。

### 来源与可追溯性

- `source_documents`：原始文档、内嵌附件和二次整理稿；
- `source_evidence`：单元格、段落或表格行级证据；
- `requirement_source_links`：需求为什么能追溯到该证据，以及是客户原述还是辅助支持。

### 适用范围

- `scope_dimensions`：机构、CAD 专业、产品领域、产品类型、组部件、图纸类型、文件格式、设计阶段、使用角色和业务系统；
- `scope_values`：沈变公司、机械设计、变压器、铁心叠片、绕组、DWG、DXF 等可扩展字典值；
- `requirement_scope_links`：某个需求包含、排除或条件适用哪些范围值，并可声明是否向下继承。

这些维度不是硬编码枚举。当前“特变电工沈阳变压器集团有限公司”仍标为根据原始访谈推定、待正式确认；“17 类”和“全品类”也没有擅自补成完整目录。

### 验收与未决问题

- `acceptance_criteria`：每个原子需求的候选验证方法、阈值和确认状态；
- `open_questions` 与 `open_question_requirement_links`：问题本体及其影响的需求。

当前生成 201 条候选验收条件，但没有资料支持的数值阈值全部留空。把验证方法写出来，是为了下一步和客户一起补阈值，并不等于我们替客户批准了验收标准。

### 图谱视图与坐标

- `graph_views`：一个业务图谱视图及其布局版本；
- `graph_view_filters`：该视图采用的机构、专业、产品领域等筛选；
- `graph_layout_positions`：`view_id + node_id + x/y/z + position_source + locked`。

坐标不放在 `BusinessRequirement` 上，因为同一个需求在“按业务层级”“按能力复用”“按运行成功率”等视图中可以处在完全不同的位置。当前 240 个位置记录的 `x/y/z` 全部为 `null`，也没有给 x、y、z 轴臆造业务含义。

## Ontology 类型和动作

类型定义在 `ontology/shenbian/v2/business-requirements.yaml`。主要对象是 `BusinessRequirement`、`RequirementRelation`、`SourceEvidence`、`ScopeValue`、`AcceptanceCriterion`、`OpenQuestion`、`GraphView` 和 `GraphLayoutPosition`。

还预留了与业务建模直接相关的动作：

- 提议拆分业务需求；
- 确认客户可读名称；
- 记录合并、拆开或复用决定；
- 设置适用范围；
- 确认原子需求验收条件；
- 用新证据关闭待确认问题；
- 审批并发布需求基线。

这符合 Palantir 把对象视为“名词”、把动作视为“动词”的做法。动作日志以后可以把每次人工确认和模型变更本身变成可分析的数据。[Action log](https://www.palantir.com/docs/foundry/action-types/action-log)

## 这批数据还没有做什么

本轮只建立业务图谱，没有提前伪造下面三类连接：

1. 业务需求到 `local-dev/cad` 01—07 logic 的连接；
2. logic 到 THCAD/.NET/COM/LISP/BRX-ARX 能力点的连接；
3. AgentRun 使用了哪些需求、logic 和能力，耗时多久、成功失败、review 如何的运行连接。

这些关系不应由文档作者凭空填写。后续 Agent 执行真实任务时，才新增 `Requirement ↔ Logic ↔ Capability ↔ AgentRun ↔ Review` 的决策谱系。Palantir 也把数据、逻辑和动作的端到端 decision lineage 视为持续优化人类和 Agent 工作流的关键。[Why create an Ontology?](https://www.palantir.com/docs/foundry/ontology/why-ontology)
