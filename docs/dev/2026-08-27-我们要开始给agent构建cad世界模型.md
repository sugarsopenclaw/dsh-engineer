懂，而且你这次抓到的是最关键的一层：**前面“两张图”的说法少了一张动态生成的“运行经验图”**。

真正的结构应该是三张相连的子图：

```text
业务图谱                    能力与 Logic 图谱
为什么做、成功是什么          能做什么、如何计算和操作

去标注任务                  02 图框检测
验收标准                    03 分区定位
输入图纸类型                04 明细知识化
业务对象                    .NET / COM / LISP 能力
     │                              │
     └──────── Agent 运行 ──────────┘
                    ↓
              运行经验图谱
       实际选择了什么、按什么顺序、
       成功还是失败、耗时、评价如何
```

## 静态建模只定义“可能怎样连接”

前期我们可以预先建立：

```text
去标注任务 MAY_USE 图框检测
图框检测 USES Line.StartPoint
序号坐标提取 USES ExplodeGeometry
图层隐藏 ACTION_USES Layer.IsOff
```

这些只是在告诉 Agent：

- 有哪些可用能力；
- 各自输入输出是什么；
- 有哪些已知候选路径；
- 有什么前置条件和风险。

它们是“可供选择的道路”，不是写死的工作流。

## Agent 运行才产生“实际怎样连接”

例如某一次真实任务：

```text
DeannotationJob#42
→ input Drawing#5TBC.384
→ executed_by AgentRun#20260827-001

AgentRun
→ 第 1 步 USED DrawingFrameDetector@v1
→ 第 2 步 USED DrawingZoneDetector@v1
→ 第 3 步 USED CadLayerAnalyzer@v1
→ 第 4 步 INVOKED DotNet.Entity.Erase
→ 第 5 步 INVOKED Database.SaveAs
→ produced DrawingVersion#cleaned-1
→ duration 73s
→ outcome accepted
→ review_score 4.7
```

这条路径以前不存在。是 Agent 为了完成一个具体业务任务，在特定图纸和特定时间下，选择并组合 Logic 与底层能力后产生的。

所以你说得完全对：

> 业务建模给出“要完成什么”；能力图谱给出“有哪些东西可以用”；Agent 的真实运行把两者连接起来。

## 真正应该积累的是“决策与执行谱系”

不是简单给 `图框检测.success_count += 1`，而是保存每一次完整运行事实：

- 属于哪个顶层业务需求；
- 输入的是哪张图、哪个版本；
- 使用了哪个 Agent、模型和规则版本；
- 每一步选择了什么 Logic；
- Logic 又使用了哪些 .NET/COM/LISP 能力；
- 读取了哪些业务对象和关系；
- 创建、修改或删除了什么；
- 中间遇到了什么观察结果；
- 为什么改变了原定路径；
- 最终成功、部分成功还是失败；
- 总耗时、各步骤耗时、模型成本；
- 是否需要人工介入；
- Review 给了什么评价；
- 输出是否最终被用户接受。

成功率、平均耗时、Review 分数都应从这些原始运行记录派生，而不是成为唯一真相。否则一次失败究竟是能力不行、图纸特殊、Agent 选错顺序，还是保存时出错，就分不清了。

## 它会形成多个可分析维度

以后我们可以问：

- 沈变所“图纸去标注”一共运行了多少次？
- 哪类图纸成功率最低？
- 成功任务最常使用哪些 Logic 组合？
- `02 → 06 → 擦除` 和 `02 → 03 → 06 → 擦除` 哪条路径 Review 更好？
- 哪个底层 API 经常出现在失败步骤？
- 中心线识别在哪些图纸类型上提高了去标注效果？
- 哪些任务需要人工介入？
- 某版本 `CenterlineIdentifier` 升级后，耗时和 Review 是否变好？
- 对当前这张图，历史上最相似的成功路径是什么？

这时图谱积累的已经不是“知识”，而是 **Agent 的工程经验**。

## Agent 确实应该自己决定怎么用

但不是毫无约束地自由发挥。

我们负责提供：

- 类型明确的业务目标和验收标准；
- 可调用的 Logic、Function 和 Action；
- 输入输出契约；
- 候选路径和历史成功路径；
- 写图、删除、保存等动作的边界。

Agent 负责：

- 根据当前图纸查询已知事实；
- 选择一条起始路径；
- 调用 02–07 或底层能力；
- 根据中间结果改变计划；
- 完成或停止任务；
- 把实际路径、观察和结果写回运行图。

也就是：

```text
预建路径 = Playbook / 建议路线
Agent 选择 = 当前决策
实际调用 = 运行事实
Review = 结果评价
多次运行汇总 = 可复用经验
```

未来的新 Agent 不会被强制重复历史路径，而是可以看到：

> 对这种图纸，过去 18 次里有 15 次使用“02→03→06→Erase”成功；平均 64 秒，Review 4.6。另一路径更快，但曾误删分区带文字。

然后它结合当前图纸决定是否沿用或调整。

这已经非常接近 Palantir 所说的 **decision lineage**：不仅记录数据和结果，还记录在什么数据版本上、使用了什么逻辑、做出了什么选择、执行了什么动作。

所以更准确的总体架构是：

```text
业务图谱       定义“为什么、什么算成功”
能力图谱       定义“有什么可以使用”
运行经验图谱   记录“Agent 实际怎样完成”
评价与统计     从运行谱系中派生“什么方法在什么场景更好”
```

前一篇文档中的“两张图”确实应该升级为这个“三图 + 时间/评价维度”的模型。你现在想到的已经不只是 CAD Ontology，而是一套能够随着真实任务运行不断积累经验的 **Agent Operating Model**。
