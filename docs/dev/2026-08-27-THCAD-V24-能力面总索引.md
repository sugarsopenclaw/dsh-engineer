# THCAD V24 能力面总索引

> 更新日期：2026-08-30
> 实测安装：`D:\THSOFT\THCAD V24_Mechanical2D`

## 0. 先说结论

THCAD 不是只有一套 API。当前已经分开盘点五个互相重叠、但不能互相替代的能力面：

1. **当前抽取 JSON 字段**：回答「现有抽取器已经保存了什么」；
2. **公开托管 .NET API**：回答「进程内公开的类型、计算、创建、修改和宿主交互入口有什么」；
3. **COM Automation**：回答「跨进程自动化对象模型和天河 COM 业务接口有什么」；
4. **LISP 与命令**：回答「当前 LISP 环境、源码函数、菜单宏和动态命令入口有什么」；
5. **原生 BRX/ARX 与 PE 导出**：回答「本机有哪些原生模块和二进制导出线索，以及是否具备可编译的公开 SDK」。

任何一份库存里没有某项，都不能直接推导为「THCAD 拿不到」。应先在总索引中查其他能力面，再对具体入口和具体对象做运行时验证。本索引不排除读取以外的创建、修改、删除、变换、保存、打印和命令能力。

## 2. 当前最重要的新发现

COM 不只是目前脚本使用的 `GetActiveObject + SendCommand`。天河自己的 `THCadToolKit` 类型库还公开了：

- `GetBomRecorder` / `SetBomRecorder` / `AddBomRecorder` / `DeleteBomRecorder`；
- `GetXuHaoLabel` / `SetXuHaoLabel` / `AddXuHaoLabel` / `DeleteXuHaoLabel`；
- `GetPaperRecorder` 以及标题栏、明细表、图幅刷新；
- DWG 打开/关闭、二维码生成、块属性写入；
- TH 图层名称与含义转换。

这些入口与我们已经从命名字典和实体中发现的明细表、序号、图幅知识高度相关，后续值得按具体需求逐个实测。成员名存在不等于参数协议、初始化条件和返回结构已经确认。

系统还注册了 6 组此前漏扫的 32 位天河业务类型库：`THCADPickUp` / `THCADPickUpEngine`、`THCADsCardInfoX` / `THCADsCardEngine`、`THCADReport` / `THCADComReport`。它们公开了单文件/批量数据提取、无效与失败文件信息、卡片/表/字段结构、卡片生成保存和报表配置。6 个代表性 ProgID 已在 32 位进程中全部实际创建成功；因为服务器是 32 位 OCX/DLL，不能直接加载进 64 位 THCAD/.NET 进程，正式复用需另设 32 位辅助进程或验证天河已有调用链。

LISP/命令盘点还证明当前 THCAD 会话中存在大量已加载业务能力；CUI 中也有大量 PCCAD/THCAD 菜单宏。它们适合发现已有工作流和快速验证，但不能把菜单宏数量误当成独立命令数量。

原生盘点证明大量 TH/PCCAD C++ 类和函数实现确实存在；同时也证明当前产品安装**没有附带公开 SDK 头文件和导入库**。因此现阶段可以把导出名用于发现线索，不能直接按猜测签名调用。

2026-08-30 视觉概览实测又确认了一条组合能力：用 .NET capability 02 提供确定性图框，COM 只验证并附着 `thcad.exe`，再经命令面 `PNGOUT` 导出 frame window。当前安装未提供可用的 raster PC3，因此没有采用元数据中虽存在但运行条件不满足的 `PlotToFile` 路径。该动作在样图上生成非空 PNG，并验证 DBMOD 前后均为 21；完整前置条件和失败记录见 [`2026-08-30-Pi-THCAD-视觉概览与晓量能力取舍.md`](2026-08-30-Pi-THCAD-视觉概览与晓量能力取舍.md)。

2026-08-30 V4 产品桥进一步验证了多文档与 side-DB 组合能力：`CommandFlags.Session` 下的 `DocumentCollection.Open`、`MdiActiveDocument` 切换和 `CloseAndDiscard` 已在真机跑通；`Database.ReadDwgFile` 无编辑器地扫描七张 DWG，生成 5,543 条项目文字/BOM 索引记录。客户图强制只读，复制/保存只允许本机 THCAD workspace。活动工作区图直接 `Database.Save()` 在本机返回 `eCantOpenFile`，而 `Document.AcadDocument.Save` 成功，因此“公开成员存在”和“当前 Document 上下文可用”仍需分层记录。详见 [`2026-08-30-Pi-THCAD-图纸会话与项目文字检索.md`](2026-08-30-Pi-THCAD-图纸会话与项目文字检索.md)。

## 3. 开发时怎么选

- 整图大量实体、精确几何、专业对象和可测试适配器：优先 .NET；
- 从 DSH/PowerShell 连接已打开 THCAD、读取应用/文档状态、触发工作流：COM；
- 快速选择、句柄、字典、命令编排和现有 UI 工作流复用：LISP/命令；
- 只有在公开 SDK、版本 ABI、性能收益和部署方式都明确时，才把原生 BRX/ARX 作为正式实现面；
- 宿主无关判断继续放 `local-dev/cad/core/`，任何 THCAD/.NET/COM/LISP 调用都留在 Adapter/Host。

这不是固定优先级。某个功能可以组合多个能力面，例如 COM 附着当前 THCAD、LISP 恢复选择集、.NET 读取实体并把普通坐标交给 Core。

## 4. 「存在」分三层记录

后续看到一个好方法时，至少区分：

1. **元数据存在**：类型库、程序集、LSP/CUI 或 PE 导出里能看到名字；
2. **运行时入口可达**：当前 THCAD/许可证/文档中能取得对象或调用方法；
3. **业务语义已验证**：返回值和实际图形关系在样图中已核实，例如 `TH_XuHaoEntity.ExplodeGeometry` 的两端坐标。

只有第三层才能直接进入稳定业务算法；前两层是值得继续验证的能力线索。

## 5. 私有实现不是一份可证明的「全量 API」

公开 .NET 之外的 internal/private 成员、未导出的 C++ 实现、动态命令和私有对象协议都可以继续研究，但不存在一个静态扫描就能证明完整的目录。适合的记录方式是：

- 先保存程序集/导出/字符串/对象行为线索；
- 对具体 `runtime_class` 或具体业务动作做小探针；
- 把成功、失败、前置条件和样本写入运行时支持记录；
- 不把反编译看到的私有名字自动当成稳定 API。

这部分不是放弃探测，而是避免把「实现线索」和「可依赖接口」混成同一件事。
