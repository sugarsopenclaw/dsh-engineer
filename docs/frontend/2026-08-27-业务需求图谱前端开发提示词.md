# 业务需求图谱前端开发提示词

> 用途：把下面整段提示词交给前端开发者或 Coding Agent。它描述的是生产实现，不是视觉 Demo。

## 为什么选这套组件

- 使用 Vite + React + TypeScript 建立独立产品前端。
- 2D 使用 `react-force-graph-2d`（Canvas），3D 使用 `react-force-graph-3d`（Three.js/WebGL）。两者的数据和交互接口接近，可以共用一套业务状态；第一版无需从裸 Three.js 场景开始搭建。
- 使用 `@tanstack/react-query` 管理真实 API 的加载、缓存、错误和重试；不要把服务端数据复制进另一套全局状态。
- 后端已经生成具有业务含义且可复现的 2D/3D 坐标。图组件只渲染这些坐标，不再自行计算随机力导向布局。

官方参考：

- [Vite Getting Started](https://vite.dev/guide/)
- [react-force-graph](https://github.com/vasturiano/react-force-graph)
- [TanStack Query for React](https://tanstack.com/query/latest/docs/framework/react/overview)

```text
你是本仓库的前端负责人。请直接完成“沈变客户业务需求图谱”的第一版生产前端，不要只写方案，也不要制作 mock 演示。

一、先读上下文

在改文件前，按顺序完整阅读：

1. 根目录 AGENTS.md：仓库边界和环境变量约定；
2. docs/backend/business-requirements-graph-api.md：本功能的真实 HTTP 契约、TypeScript 类型、坐标语义、错误码和联调顺序；
3. docs/backend/api.md：后端通用约定和健康检查；

6. docs/dev/2026-08-27-沈变客户需求业务Ontology建模.md：本批业务建模的来龙去脉。

不要读取或改写 client-data/ 中的客户原始文件。不要改 harness/、backend/、ontology/、data/ 或 plugins/。如果真实 API 与契约不一致，记录具体请求、响应和差异，停止用前端补丁掩盖后端问题。

二、工作目录和技术栈

在仓库根目录新建独立的 frontend/，全部前端代码、测试、锁文件和前端 README 都放在这里。不要把代码塞进 harness/，也不要把 frontend/ 加入 harness 的 pnpm workspace。

- Vite + React + TypeScript（react-ts 模板，TypeScript strict）；
- pnpm，并提交 pnpm-lock.yaml；
- react-force-graph-2d：2D Canvas 图；
- react-force-graph-3d：Three.js/WebGL 3D 图；
- @tanstack/react-query：服务端状态、缓存、错误与重试；

不要直接从 Three.js 手写整套图引擎。若 3D 节点确实需要自定义 Object3D，再在 react-force-graph-3d 的扩展点中少量使用 Three.js。

三、只连接真实 API

运行时只调用：

- GET /api/v1/business-requirements/graph?dimensions=2
- GET /api/v1/business-requirements/graph?dimensions=3
- GET /api/v1/business-requirements/{requirement_id}
- 可选：GET /api/v1/health/live，用于明确提示后端是否启动。

Vite 开发服务器把 /api 代理到 http://127.0.0.1:8000。浏览器始终请求同源相对路径 /api/v1/...，不要为了本机开发扩大后端 CORS，也不要在源码里散落绝对后端地址。

严禁在生产代码中放 mock 节点、fixture fallback、随机生成数据或“接口失败就展示示例图”的逻辑。后端不可用时，页面必须明确显示错误、请求地址和重试按钮。测试目录可以使用最小 fixture 或网络替身，但它们不得进入生产 bundle，也不得成为运行时降级数据源。

第一版不需要前端环境变量，不要在 frontend/ 再建 .env。以后确有 VITE_* 配置时，Vite 的 envDir 必须指向仓库根目录；任何密钥都不能使用 VITE_*，也不能进入浏览器。

四、坐标是业务数据，不是装饰

后端 initial-semantic-v1 已经稳定计算坐标：离原点越近，越贴近客户原始需求表达；离原点越远，越偏向规范化组织或领域拆分。除此以外，角度、象限、正负 Z 和同一圈内先后暂时没有业务含义。

将 API 节点映射为图引擎节点时：

- x/y/z 取 node.position.x/y/z；
- position.locked=true 时，同时设置 fx/fy/fz，把节点锁在服务端位置；2D 至少设置 fx/fy；
- 保留 position.radius 和 source_proximity_rank 供图例和调试使用；
- 关闭或立即冷却组件自己的力模拟，验收时刷新页面节点不得漂移；
- 2D 请求 dimensions=2，3D 请求 dimensions=3，不要在浏览器里从一套坐标猜另一套；
- 不要重算半径，不要用连线力改变节点离原点的距离。

API DTO 与图引擎对象必须分开。每次根据 DTO 派生一份 GraphRenderNode/GraphRenderLink；不要把接口响应对象直接交给图库后再当 API 原值使用，因为图库可能给节点追加运行时坐标，或把 link.source/link.target 从 ID 改成对象。选中状态、详情缓存和邻接关系都以稳定的 requirement id 为准。

五、页面要实现什么

做一个桌面优先、可实际观察业务建模结果的工作台：

1. 顶栏：页面标题、2D/3D 切换、搜索、适配全图、重置视角；
2. 左侧控制区：总节点/边/原子需求/一级需求/待确认数量，以及筛选器和完整图例；
3. 中央画布：缩放、平移或旋转、悬停、点击选择、关系高亮；
4. 右侧详情抽屉：节点基础信息、父子关系、别名、来源证据、适用范围、候选验收条件、待确认问题；
5. 明确显示布局说明：“越靠近中心，越贴近客户原始需求”；
6. 加载、空结果、后端离线、接口错误都要有完整状态，不允许白屏。

筛选至少支持：

- 文本搜索（id、名称、描述）；
- origin_kind；
- requirement_kind；
- atomic；
- needs_confirmation；
- customer_visible。

筛选发生在前端。过滤后只保留两个端点都可见的边；同时显示“当前可见 / 总数”。清空筛选能恢复完整图。不要把当前 240/249 写死进组件，所有计数取响应；240 个节点、249 条边只是当前真实数据集的联调基线。

节点视觉只表达接口已有事实，并给出图例：

- origin_kind 可使用三种分类颜色，未知值必须有默认样式；
- 根节点单独可识别；
- atomic 与非 atomic 可用大小或轮廓区分；
- needs_confirmation 可用外圈或标记区分；
- 标签优先显示根节点、一级需求、悬停节点和选中节点，避免 240 个长标签同时覆盖画布。

边按 contains_requirement、decomposes_to、reuses_requirement 区分颜色或线型，未知 relation_kind 有默认样式。悬停或选择节点时，高亮直接父子/复用邻居，弱化其余节点和边；点击相邻节点也能打开详情。

2D 与 3D 共用搜索、筛选、选中 requirement id、图例和详情状态，只替换渲染器与相机状态。切换维度后应继续选中同一个需求；如果该节点仍可见，将镜头定位到它。使用 ResizeObserver 或等价机制让画布适应容器，不要假设固定窗口尺寸。

详情只在用户点击节点后请求，不要在首屏并发请求 240 份详情。verbatim_text 是客户资料正文：只在详情抽屉中按需显示，不写入 URL，不做 localStorage/IndexedDB 持久缓存，不发送到分析服务。TanStack Query 只使用内存缓存。

六、交互与可用性底线

- 搜索和筛选控件有 label，键盘可操作；详情抽屉可用 Escape 关闭并正确管理焦点；
- 不依赖颜色作为唯一信息通道；
- 画布悬停只更新必要状态，不在 pointer move 中重建整张图；
- graphData、邻接索引和筛选结果使用稳定 memoization；
- HTTP client 必须检查 response.ok，并解析 FastAPI detail 错误；错误信息不能泄露连接串、绝对路径或密钥；
- 不增加写接口、拖拽持久化、登录、远程部署鉴权、AgentRun/Logic/Capability 混合视图，这些不在第一版范围内；
- 可以允许临时拖拽观察，但松开后要回到或提供按钮恢复服务端坐标，不能让用户误以为位置已经保存。

七、验证和交付

至少覆盖这些自动化测试：

- API DTO 到 2D/3D 图节点的映射，特别是 x/y/z 与 fx/fy/fz；
- 筛选节点后不会留下悬空边；
- 2D/3D 切换保留选中 id；
- 点击节点后才请求详情；
- 404、422、503 或后端离线时显示错误和重试，不展示假数据；
- 未知枚举值使用默认样式而不是崩溃。

完成后运行并报告：

- pnpm lint
- pnpm test --run
- pnpm build

再用真实后端做人工联调：从仓库根双击 start-backend.cmd，或运行 .\scripts\start-backend.ps1；然后在 frontend/ 运行 pnpm dev。确认当前数据能显示 240 个节点、249 条边，2D/3D 坐标稳定，BR-000 位于原点，点击节点能读到真实详情。代码里不能依赖这些固定数量。

frontend/README.md 必须写清安装、开发、测试、构建、真实后端启动方式、使用的 API、坐标含义以及“运行时无 mock”。最后给出新增/修改文件列表、验证命令结果、真实 API 联调结果和仍未实现的明确边界。
```

## 交付时的审查重点

审查前端时，优先看三件事：坐标有没有被图库重新计算、接口失败时有没有偷偷回退到假数据、详情正文有没有被不必要地批量加载或持久化。界面是否炫酷排在这三件事之后。
